# ВышКат — учёт парка кикшеринга

Приложение консольного типа на C# .NET 8, предназначенное для учёта транспорта и имущества оператора «ВышКат». Оно покрывает обязательные сценарии ДЗ №1 по конструированию программного обеспечения: ведение парка, автоматический техосмотр, инвентаризацию, расчёт суточного энергопотребления, формирование списка транспорта для новичков. Дополнительно реализованы принципы SOLID, внедрение зависимостей через DI-контейнер и модульные тесты.

## Требования для запуска

- .NET SDK **8.0** (проверить установку: `dotnet --version`).
- Доступ к NuGet для первого восстановления пакетов `Microsoft.Extensions.DependencyInjection`, xUnit и тестовых компонентов.
- Windows, Linux или macOS с консолью, поддерживающей UTF-8.

В корне архива выполните:

```bash
dotnet restore Vyshkat.sln
dotnet build Vyshkat.sln -c Release
dotnet run --project Vyshkat.Console
```

Завершение работы — пункт `7`. Между запусками данные не сохраняются, весь инвентарь находится в оперативной памяти. В основном приложении нет заранее созданных демонстрационных объектов: все данные вводятся пользователем.

## Меню и функциональность

```text
1. Добавить транспорт
2. Добавить вещь
3. Показать весь инвентарь
4. Показать транспорт для новичков
5. Отчёт по инвентарю
6. Энергопотребление
7. Выход
```

**Транспорт**: электросамокат, обычный велосипед, электровелосипед, электрокар. Пользователь указывает вид транспорта, его ID, простоту для новичка по шкале от 1 до 10, исправность тормозов и рулевого управления. Для электротранспорта дополнительно вводятся заряд батареи (0–100) и суточный расход электричества (кВт·ч).

**Вещи:** шлем, зарядная станция, аптечка первой помощи. Суточный расход энергии указывается пользователем лишь для зарядной станции; прочие вещи электричество не потребляют. Вещи не проходят техосмотр, который предусмотрен для транспорта.

**Техосмотр:** `CheckVehicle` пропускает транспорт при исправных тормозах, исправном управлении и (для электротранспорта) заряде не ниже 30%. В случае отказа выводится его причина, транспорт в парк не попадает, пользователь возвращается в основное меню. Заряд 25% — это корректные исходные данные, но основание для отказа при приёмке; заряд 150% — некорректный ввод, поэтому запрашивается заново. На прохождение техосмотра показатель простоты не влияет.

**ID:** уникальное положительное целое число для всего инвентаря (у транспорта и вещей общая область уникальности). Вид транспорта и его ID хранятся раздельно. Если ID повторяется, интерфейс предлагает ввести другой номер, не требуя повторного ввода остальных характеристик. При некорректном значении отдельного поля запрашивается повторно только это поле.

**Новичок:** учитывается только принятый транспорт, у которого `EaseOfUse` >= 6 (граница 6 включается). Отчёт по инвентарю отдельно отображает число транспортных средств, вещей и общее количество объектов. Отчёт об энергопотреблении складывает расход всех объектов с интерфейсом `EnergyConsumer` — электротранспорта и зарядных станций. Расход выражается в кВт·ч за сутки.

### Распределение ответственности

- `IInventory` задаёт универсальный контракт инвентаризируемого объекта и используется как тип результата `GetItems`, `InventoryItem` реализует его и централизованно проверяет положительность ID. `Vehicle` добавляет характеристики транспорта, `ElectricVehicle` — заряд и энергопотребление. `Helmet`, `ChargingStation`, `FirstAidKit` — отдельные категории вещей.
- `VehicleFactory.CreateVehicle(VehicleType type, VehicleData data)` создаёт конкретный транспорт. `VehicleData` не хранится в парке; это только набор исходных параметров создания. Фабрика не выполняет техосмотр и не общается с консолью.
- `ServiceCenter.Inspect(Vehicle)` описывает проверку, `CheckVehicle` реализует правила. `InspectionResult.Approved` — решение, `InspectionResult.Denied` — причина отказа или пустая строка при успехе.
- `InventoryManager` содержит одну `List<InventoryItem>`, методы `AddVehicle`, `AddItem`, `GetItems`, `GetBeginnerVehicles`, `GetInventoryReport`, `GetEnergyConsumption`. До внесения транспорта в коллекцию вызывается `ServiceCenter`. `AddItem` запрещает добавлять экземпляр `Vehicle` в обход техосмотра. Повторный ID и отказ техосмотра возвращаются через `OperationResult.Success` / `OperationResult.Message` без исключений.
- `ConsoleMenu` спрашивает данные, обрабатывает пользовательские ошибки и отображает результаты. Доменная модель и фабрика дополнительно защищены исключениями от некорректных параметров, полученных не через консоль.

В `Program.cs` контейнер `Microsoft.Extensions.DependencyInjection` связывает `ServiceCenter` → `CheckVehicle` и создаёт `InventoryManager`, `VehicleFactory` и `ConsoleMenu`. Данные в одном `InventoryManager` сохраняются во время всего сеанса благодаря регистрации `AddSingleton`.

## SOLID — обоснование каждого принципа

**S (Single Responsibility Principle).** `ConsoleMenu` отвечает только за ввод и вывод, `VehicleFactory` — за создание транспорта, `CheckVehicle` — за техосмотр, `InventoryManager` — за учёт и получение агрегированных сведений. Формирование отчёта и вычисление энергии — отдельные методы. Ради небольшой предметной области они пока находятся в одном менеджере, без искусственного разбиения на сервис для каждого метода.

**O (Open/Closed Principle).** Новый транспорт может наследоваться от `Vehicle` или `ElectricVehicle`; общие проверки `CheckVehicle`, фильтр новичков и учёт энергии не потребуют переписывания. Однако отображение нового вида в меню и переключатель в `VehicleFactory` нужно будет расширить (см. сознательное ограничение ниже).

**L (Liskov Substitution Principle).** `Bicycle`, `ElectricScooter`, `ElectricBike`, `ElectricCar` являются корректными `Vehicle`: все имеют ID, показатель простоты, тормоза и управление. `InventoryManager` работает с `Vehicle`, не спрашивая его конкретный тип. `ElectricVehicle` дополнительно реализует интерфейс потребления электричества.

**I (Interface Segregation Principle).** Отдельный `EnergyConsumer` содержит только `EnergyConsumption`: обычный велосипед, шлем и аптечка не обязаны реализовывать ненужное им свойство. `IInventory` содержит только ID и название, а `ServiceCenter` — только операцию осмотра.

**D (Dependency Inversion Principle).** `InventoryManager` зависит от интерфейса `ServiceCenter`, а не от класса `CheckVehicle`. В обычном запуске реализацию назначает DI-контейнер, а в тестах она заменяется на `FakeServiceCenter`. Соответствующие примеры: `InventoryManager.cs`, `Program.cs`, `InventoryManagerTests.cs`.

### Сознательно ограниченный принцип

**OCP ограничен на границе создания и меню.** `VehicleFactory.CreateVehicle` использует `switch` по `VehicleType`, а `ConsoleMenu` — фиксированный выбор из четырёх пунктов. Добавление пятого вида потребует добавить значение в `VehicleType`, ветку фабрики и пункт консольного выбора. Для четырёх известных типов это проще и прозрачнее, чем регистрируемые обработчики/плагины и дополнительные фабричные интерфейсы; общий учёт и правила проверки при этом останутся нетронутыми. Такое ограничение предотвращает overengineering.

### Что произойдёт при расширении

- **Новый электротранспорт:** создаётся наследник `ElectricVehicle` (при необходимости — в отдельном файле), добавляется вариант `VehicleType`, ветка фабрики и пункт меню. `InventoryManager`, `CheckVehicle`, агрегирование энергопотребления и фильтр для новичков продолжают работать без изменений.
- **Сотрудники:** по условию они **не инвентаризируются**, поэтому нельзя просто добавить сотрудника в `List<InventoryItem>`. Понадобятся отдельные модель, коллекция/сервис и сценарии взаимодействия, без изменения текущего учёта транспорта.
- **Склад запчастей:** можно ввести отдельный сервис складского учёта или объекты имущества, если запчасти должны стоять на балансе. Текущие способы расчёта энергопотребления не зависят от новых неэлектрических предметов.

В учебном проекте несколько небольших родственных классов намеренно находятся в одном файле (`Vehicle.cs`, `ElectricVehicle.cs`). На принципы SOLID это не влияет: классы независимы по смыслу, даже если размещены вместе.

## Юнит-тесты и подмена техосмотра

```bash
dotnet test Vyshkat.sln
```

Для сбора покрытия через установленный `coverlet.collector`:

```bash
dotnet test Vyshkat.Tests/Vyshkat.Tests.csproj --collect:"XPlat Code Coverage"
```

Результат будет сохранён в каталоге `Vyshkat.Tests/TestResults/` (файл `coverage.cobertura.xml` в подкаталоге запуска). Ориентир из задания — покрытие не менее 60%; **проверить реальный процент необходимо по отчёту запуска**.

- `CheckVehicleTests`: настоящий техосмотр, исправность систем, граница заряда 29/30%, успешный велосипед без батареи.
- `InventoryManagerTests`: регистрация `FakeServiceCenter` в DI-контейнере вместо `CheckVehicle`, принятие и отказ независимо от технических свойств, блокировка повторных ID (между транспортом и вещами), защита от обхода техосмотра, возможность снова использовать ID отклонённого транспорта.
- `ReportTests`: правильные количества транспорта/вещей, нулевые отчёты пустого парка, граница простоты 5/6, исключение отклонённого транспорта из выборок и энергопотребления, учёт зарядных станций.
- `VehicleFactoryTests`: все четыре вида, обязательные электрические свойства, неизвестный вид и некорректные параметры объектов.

В `FakeServiceCenter` результат заранее настраивается через `Approved`; проверяются вызовы через `InspectionCount`. Это позволяет тестировать поведение `InventoryManager`, не связывая его с реальными правилами `CheckVehicle`.

## Сценарии для ручной демонстрации

1. В пустом парке откройте пункты 3–6: списки пусты, количества равны нулю, энергопотребление 0.
2. Добавьте исправный велосипед, выбрав простоту **6**. Проверьте, что он появился в инвентаре и в списке для новичков, но не увеличил энергопотребление.
3. Добавьте исправный электросамокат с зарядом **30%** и положительным энергопотреблением: он должен пройти техосмотр. При простоте 5 он не должен появиться в списке для новичков.
4. Попробуйте добавить электрокар с зарядом **29%**. Программа объяснит отказ и вернётся в меню; автомобиль не появится в отчётах.
5. Попробуйте добавить транспорт с неисправными тормозами или управлением. Появится соответствующая причина отказа.
6. Добавьте шлем, зарядную станцию и аптечку; проверьте общую нумерацию и то, что в суммарной энергии учитывается расход станции.
7. Попробуйте занятый ID при добавлении транспорта и вещи; программа попросит заменить **только ID**, сохранив остальные введённые характеристики.
8. Введите некорректную простоту 11, заряд 150%, отрицательный расход или буквы вместо ID: программа повторит запрос только ошибочного поля.
9. Откройте пункты 3–6 ещё раз: все отчёты должны учитывать **только принятое** имущество. Завершите работу пунктом 7.

## Ограничения решения

Данные хранятся исключительно в памяти; авторизация, аренда, пользователи и база данных отсутствуют, так как они не требуются домашним заданием. Расход энергии вводится пользователем как суточная характеристика устройства, а не рассчитывается на основе пробега и зарядных циклов. ID уже поставленного на баланс объекта изменять нельзя. Проект рассчитан на одного консольного оператора за раз; потокобезопасность коллекции не реализована, поскольку многопользовательский доступ отсутствует.
